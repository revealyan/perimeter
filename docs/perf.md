# Производительность: замеры и оптимизации

## Замеры (bench.ts, локально, 2026-11-10)

| Событий | Размер кадра | Время | Скорость |
|---|---|---|---|
| 2 000 | 200 байт | 108 мс | **18 519/сек** |
| 5 000 | 1 000 байт | 261 мс | **19 157/сек** |
| 10 000 | 100 байт | 577 мс | **17 331/сек** |

**Вывод: сеть и supervisor — не узкое место.** Пропускная способность WSS + фанаут ~19K событий/сек — на 3 порядка выше реальной нагрузки (~500/сек в худшем случае стриминга).

## Где было узкое место и как полечено

### N1: React-ререндер на каждый кадр (главная причина «подлагивания»)

**Было:** каждый `event:*` из WSS вызывал `notify()` → полный ререндер React-дерева (лента + сайдбар + панель). При стриминге ~500 событий/сек — 500 ререндеров/сек.

**Стало:** rAF-коалесценция (рецепт из Claude Code: Ink тоже троттлит до 10–30 флашей/сек):
- `notify()` планирует один флаш через `requestAnimationFrame`
- все промежуточные мутации применяются, рендерится только последний кадр
- в фоне окна (rAF не работает) — фолбэк на `setTimeout(33)` (~30/сек)
- максимальная частота ререндера: **60/сек** (видимое окно) / **30/сек** (фон)

### N1b: CSS-анимации появления (рецепт CC: fade-slide 120ms)

```css
.bubble, .card, .turn-chip { animation: fadeSlideIn 120ms ease-out; }
@keyframes fadeSlideIn { from { opacity: 0; transform: translateY(4px); } to { opacity: 1; transform: none; } }
```

Плюс скелетоны ленты (три яруса загрузки — мгновенно/скелетон/шаги), `prefers-reduced-motion`.

### N2: холодный старт claude-процесса (SDK prewarm/SpareProcess)

**Было:** первый `query()` → spawn + init → **~1–3 сек** до `system/init`.

**Стало:** `PrewarmPool` держит N прогретых процессов; `session.new` забирает через `claim()` → init в мс. Настройка `PERIMETER_POOL_SIZE` (дефолт 1). Цена: каждый spare ~230–260 МБ резидентно.

## .NET/AOT вердикт (полный отчёт — docs/dotnet-analysis.md)

**Нет.** Единственный «проблемный» компонент — React-рендер (N1, уже исправлено). Backend простаивает: supervisor I/O-bound, оба стека сидят в ~0.1% CPU. SDK существует только для Node/TS — переписывание = форк протокола с ручной синхронизацией (~100 релизов/год upstream).

## Догон после обрыва (bench: disconnect/reconnect)

Обрыв на ~30% потока → реконнект через 2 сек → **догон ~1200 событий за <100 мс** (ring buffer + seq). Для пользователя: без разницы — лента идентична.

## Что ещё можно (если понадобится)

- **Виртуализация ленты** — если сессии станут >1000 сообщений в DOM (сейчас: все элементы в React-дереве). При текущем размере сессий (<100 сообщений) — не требуется.
- **Web Worker для base64 картинок** — если будем слать >5 МБ изображений (сейчас парсинг в главном потоке мгновенный).
