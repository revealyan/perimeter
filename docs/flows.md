# Флоу Perimeter (сводка владельца на 23.11, сверено с кодом)

`Статус 23.11` — что изменилось после сводки.

## 1. «Обычный человек» (поставка = сама себе onboarding)

1. Скачал `perimeter-setup-<версия>.exe` из GitHub Releases → поставил → открылось окно.
2. «Этот компьютер» поднимается сам: бандл supervisor'а едет в установке, движок (node-pty + Claude Code CLI)
   докачивается в профиль при первом включении — один раз на версию.
3. «Добавить аккаунт» (OAuth-окно или ключ API, например z.ai) → первая задача.
4. VPS: «+ Подключение» → адрес/ssh-юзер/ключ → «Проверить» → «Supervisor на сервере» → «Установить»
   (под root спросит пользователя службы) → Node → Claude Code → node-pty → systemd-служба → проверка hello.
5. Всё: обе среды в одном окне, «Ждут тебя» общий.

- До релизов: то же из репо (`git clone` → `npm install` → `npm run desktop`).
- Обязательного после exe — ничего (git — для git-фич; ssh-ключ — только для VPS).

`Статус 23.11:` п. 2 — докачка ~153 МБ (на диске ~330 МБ), с 23.11 видны мегабайты и «распаковываю…», зависание
даёт ошибку через 60 с, повтор не качает готовое. П. 4 заменяется флоу «IP + пароль → всё само»
(`docs/design/onboarding.md`): без ключа заранее, без вопроса про пользователя, пакеты/браузер/docker/ключ GitHub
— шагами установки.

## 2. Релизы

1. Поднял версию в `apps/desktop/package.json` → коммит → push в main.
2. `git tag v<x.y.z> && git push origin v<x.y.z>`.
3. CI (`.github/workflows/release.yml`): тесты → typecheck → сборка → electron-builder (NSIS + portable) →
   **сразу опубликованный** GitHub Release (latest) с exe + SHA256SUMS и заметками из коммитов (с v0.2.5; до него — черновик).
   Публикует один шаг `gh release create` (с v0.2.8): проверяет тег = версия и что все пять файлов на месте.
4. Откат = прошлый релиз там же. Плохой релиз — снять в GitHub (Releases → Delete) и выпустить следующий.

- Правила: тег = версия package.json (CI сверяет); electron-builder сам не публикует (`--publish never` в `dist`;
  `EP_PUBLISH` он не знает — на теге публиковал сам, отсюда двойные v0.2.7/v0.2.8); electron запинен.
- Перед тегом: `npm test` → `npm run typecheck` → живой прогон packaged-механики: `ensureLocalServer` +
  `supervisor.mjs` (отдельный порт) + **настоящий ход** (hello недостаточно).
- **Коммит перед тегом проверять** (`git log -1`): 23.11 тег v0.1.1 ушёл на старый коммит, потому что коммит
  упал (нет git-имени на VPS), а тег создан следом; тег удалён, релиз — v0.1.2.

- Живой прогон сервера без токенов: `npx tsx packages/supervisor/scripts/e2e-bundle.ts` (собранный бандл отдельным
  процессом + настоящий Claude Code + подставной шлюз) и `e2e-gateway.ts` (то же из исходников, больше проверок).

`Статус 23.11:` тестов 649. v0.1.2: докачка проверена на настоящем npm с Linux. v0.2.0: e2e-bundle 5/5, e2e-gateway 8/8;
настоящий ход на `claude.exe` — только на Windows (владелец).

## 2а. Обновление (с v0.2.7)

- **Приложение** (установленная версия, NSIS): electron-updater смотрит GitHub Releases при запуске и раз в 4 часа,
  качает в фоне (latest.yml и .blockmap прикладывает CI), в строке статуса — «Перезапустить: vX»; «Настройки → Общие» —
  версия и «Проверить обновления». Portable не обновляется сам — ссылка на страницу релизов.
- **Supervisor на серверах** — за приложением: при подключении, если там прошлая версия и в сессиях нет идущих ходов,
  обновляется сам (идут — ждёт и пробует раз в 2 минуты, до часа); ход — тостом в окне. Только где supervisor поставлен
  установщиком и только в packaged-приложении. Выключается в «Настройки → Общие».

## 3. Обновление движка Claude Code (план)

Движок — отдельный слой: `cli/<версия>/` + current; проверка свежести по npm; «Обновить движок» → докачка в
соседнюю папку → следующий старт сессии на новом; откат кнопкой. Каналы: стабильный / fresh. Подробно —
`docs/design/environment.md` §2. Приложение обновляется своим релизом (потом electron-updater).

## 4. Выкладка и обновление сервера на VPS

- Кнопка в настройках подключения («Установить/Обновить до…», откат там же); CLI-дубль:
  `npm run server:install -- <id|имя> status|install [юзер]|rollback`.
- На сервере: `~/.perimeter/server/<версия>/` + `current`, `previous` → откат; `journalctl -u perimeter`.
- Обновил приложение → обнови сервер кнопкой (блок показывает сверку версий).
- Данные (профили, accounts, state, `thinking.log`) — в `~/.perimeter` рядом с `server/`, обновление их не трогает.
- Перезапуск прерывает идущие ходы (кнопка просит подтвердить); сессия, через которую идёт разработка, сама себя
  не обновляет — жмёт владелец.

## 5. Git-пуш с VPS

- У пользователя службы ssh-ключ (`perimeter-velohost`, 23.11), публичный — в GitHub владельца.
- Сессия: `git remote add origin git@github.com:revealyan/<repo>.git && git push -u origin main`.
- Репо создаёт владелец; чтобы агент создавал сам — `gh` + `gh auth login` под пользователем службы (не сделано).
- В репозитории perimeter на VPS задано git-имя (`revealyan`, локально в репо).

`Статус 23.11:` в onboarding — генерация ключа и проверка `ssh -T` из приложения.

## 6. Перенос сессии между средами (T-ряд)

- «⋯» → «Перенести в другую среду…» (или перетащить строку в секцию другой среды).
- План (проект по имени, аккаунт цели, сверка коммитов) → export (история + настройки, источник в архив) →
  import (транскрипт в папку проекта цели, сессия остывшая, первый ход поднимет с историей).
- Патч правок — только при совпавших HEAD; untracked не едут (предупреждение). Отмена в тосте — пока цель dead.

`Статус 23.11:` журнал размышлений (`thinking.log`) при переносе не едет — у перенесённой сессии старые размышления
не покажутся.
